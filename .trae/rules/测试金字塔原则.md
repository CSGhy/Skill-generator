# 测试金字塔原则

## 一、核心思想

测试应该分层编写，越底层的测试越多，越上层的测试越少。

```
        /       \
       /  E2E    \  ← 10% 端到端/UI测试
      /-----------\
     /  集成测试   \  ← 20% 接口/模块集成
    /---------------\
   /   单元测试      \  ← 70% 函数/组件级
  /___________________\
```

## 二、各层测试说明

### 第1层：单元测试（Unit Test）—— 70%

**测什么：**
- 单个函数、方法、组件
- 工具类、算法逻辑
- 状态管理逻辑
- 表单校验规则

**特点：**
- 执行速度快（毫秒级）
- 不依赖外部资源（DB、网络、文件系统）
- 使用 Mock / Stub 隔离依赖
- 失败定位精准

**覆盖率目标：**
- 核心业务逻辑：行覆盖率 ≥ 80%
- 工具类/通用方法：行覆盖率 ≥ 90%
- 复杂算法：分支覆盖率 100%

### 第2层：集成测试（Integration Test）—— 20%

**测什么：**
- 模块之间的调用关系
- API 接口（后端接口、前端调用后端）
- 数据库交互
- 与第三方服务的集成

**特点：**
- 验证模块协作是否正确
- 可以依赖真实的数据库/服务（测试环境）
- 执行速度中等（秒级）

**重点场景：**
- 接口参数校验
- 数据持久化正确性
- 服务间调用链路
- 错误处理与降级逻辑

### 第3层：端到端测试（E2E / UI Test）—— 10%

**测什么：**
- 完整业务流程
- 用户真实操作路径
- 跨系统的端到端场景

**特点：**
- 最接近真实用户场景
- 执行速度慢（分钟级）
- 维护成本高（UI 变化就容易挂）
- 不稳定因素多（网络、环境、时序）

**选择原则：**
- 只测 P0 级核心主流程
- 不测边缘场景和异常分支
- 数量控制在几十条以内

## 三、核心原则

### 原则 1：能在底层测的，就不要往上层推

- 边界值、异常分支 → 单元测试
- 模块协作 → 集成测试
- 业务主流程 → E2E 测试

### 原则 2：测试前移

- 开发阶段就写单元测试（TDD 或开发后立即补）
- 提测前确保单元测试全通过
- 不要把所有测试压力都堆给测试团队的黑盒测试

### 原则 3：成本与收益平衡

| 测试类型 | 编写成本 | 执行速度 | 定位精度 | 稳定性 |
|---------|---------|---------|---------|-------|
| 单元测试 | 低 | 快 | 高 | 高 |
| 集成测试 | 中 | 中 | 中 | 中 |
| E2E测试 | 高 | 慢 | 低 | 低 |

## 四、反模式（避免这样做）

### ❌ 冰淇淋蛋筒模式
- 单元测试极少
- 大量依赖 UI 自动化
- 执行慢、不稳定、维护成本爆炸

### ❌ 倒金字塔
- 上层测试比下层多
- 一个 bug 要排查半天

### ❌ 只有 E2E
- 啥都想通过 UI 测
- 跑一次要几小时
- 挂了也不知道哪层出的问题

## 五、落地建议

1. **新项目**：从第一天就遵守金字塔，核心逻辑必须有单元测试
2. **老项目**：不要追求完美覆盖率，新代码/改动代码补单测，逐步还债
3. **Code Review**：MR/PR 中必须包含对应测试，否则不合并
4. **CI 门禁**：单元测试不通过不能合并，集成测试不通过不能发布
