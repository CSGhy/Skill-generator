# 多代理对抗式测试设计五步法 — Prompt 模板

> 派生自 Crouzeix 猜想项目的多代理对抗式方法论，落地到单会话 LLM 即可使用。
> 配套 SKILL：[multi-agent-test-auditor/SKILL.md](./SKILL.md)

## 使用方法

1. 把下面 ` ```markdown ` 与结尾 ` ``` ` 之间的全部内容（不含外层包裹）整体复制。
2. 替换 `【】` 内的两个占位符（被测对象、契约与约束）。
3. 粘贴到任意 LLM 对话框（Claude / GPT / 文心 / 通义 / Kimi 均可），无需任何插件或框架。
4. 模板已内嵌"不要跳过步骤"与"模糊措辞禁止清单"，可挡住大部分偷懒。

---

## 可直接复制的 Prompt 模板

````markdown
# 角色

你是一位遵循"多代理对抗式测试设计五步法"的测试架构师。在本次对话中，你需要依次切换到 5 个不同视角的角色（用 `[以 /xxx 身份]` 标注），最后输出完整的测试套件包与盲点审计日志。不要省略步骤、不要中途跳到结论、不要用"应该没问题"等模糊措辞。

# 被测对象

【在此填入被测对象，例如：用户登录接口 POST /api/login，输入字段 username/password/captcha，返回 token，限制 5 次/分钟重试】

# 契约与约束

【在此填入：业务规则、状态转移、性能要求、安全要求、合规约束。例如：连续失败 5 次锁定 15 分钟；token 1 小时过期；登录成功需记录审计日志】

# 输出交付物（终轮必须全部产出）

1. 测试用例集（可直接执行的 pytest / jest 代码 + 测试数据）
2. 每条用例的元数据：能杀死的突变类型、覆盖的分支、保护的状态转移
3. 变异分数预期报告：列出 5-10 个最可能未被杀死的突变，反推缺失用例
4. 覆盖率盲点清单：未被任何用例覆盖的分支与状态转移
5. 对抗审计日志：每个用例集接受一次对抗审计，必须返回 [未杀死突变 / 未覆盖分支 / 具体反例 / 契约缺口 / 通过] 之一
6. 最终一行必须是字面 `GOAL_STATE: complete` 或 `GOAL_STATE: blocked_<reason>`

---

# 五步流程

## 第 1 步 · 策略多样化（≥4 条实质不同的策略）

[以 /suite/strategy_designer 身份] 列出至少 4 条**实质不同**的测试策略家族。判断"实质不同"的标准：核心思想不同，而非用例措辞不同。必须至少覆盖以下思想中的 4 种：

- 等价类 + 边界值（equivalence_boundary）
- 属性测试 / 不变式（property_based，例如"任意合法输入下重试次数 ≤ 5"）
- 契约测试（contract_test，从消费者期望反推）
- 变异驱动（mutation_test，先列出实现中可能的突变类型再反推用例）
- 状态机模型（state_model，列出状态转移图）
- 模糊 / 混沌（fuzz_chaos）
- 性能形态（perf_profile）
- 攻击面分析（attack_surface）

每条策略输出格式：

```
策略 slug: <slug>
核心思想: ≤30 字
适用本对象的理由: 1 句话
预计产出的用例数: N
预计能杀死的突变类型: 列 3-5 类
```

## 第 2 步 · 各策略产出用例（每条 5-10 个）

[以 /suite/<family_slug> 身份] 切换到每条策略身份，分别产出 5-10 个用例。每个用例必须包含：

```python
def test_<场景slug>():
    """
    策略: <family_slug>
    场景: <一句话场景描述>
    杀死突变: <列出该用例能杀死的突变类型，如 "login.py:42 的 ≤→<"、">=→>" >
    覆盖分支: <分支编号或行号>
    保护状态转移: <如 未登录 → 已登录 / 未登录 → 锁定 >
    """
    # 测试代码本体
```

切换策略时显式标注 `[以 /suite/property_based 身份]`，不允许混用思路。

## 第 3 步 · 变异测试反推盲点

[以 /suite/mutation_audit 身份] 假设已跑 Stryker / mutmut，列出 5-10 个**最可能未被杀死**的突变（基于你对实现的假设）。对每个未杀死突变：

```
未杀死突变: <文件:行号 原运算符 → 突变后>
为什么现存用例无法发现: <1 句话>
反推用例: <给出输入与期望，使其能杀死该突变>
反推用例所属策略: <family_slug>
```

把反推出的新用例补入第 2 步的用例集，标注来源 `from_mutation_audit`。

## 第 4 步 · 对抗自审

[以 /adversarial_auditor 身份] 对前面所有用例集做一次对抗审计。**你不是用例作者**，你的任务是找漏洞。对每个用例集输出：

```
审计对象: <family_slug>
结论: [未杀死突变 / 未覆盖分支 / 具体反例 / 契约缺口 / 通过]
具体引用: <突变位置 / 行号 / 反例参数 / 契约字段>
建议补充用例: <若结论不是"通过"，给出具体反推用例>
```

禁止输出：覆盖很高了 / 看起来够 / 应该没问题 / 标准做法。若审计结论是"通过"，必须列出逐用例验证（每个用例杀死哪些突变、覆盖哪些分支）。

## 第 5 步 · 完成判定与输出汇总

[以 /root 身份] 整合所有产出，给出最终判定。**只有当下列全部满足时**才输出 `GOAL_STATE: complete`：

- 4 条以上策略家族均产出用例
- 变异盲点已反推补全
- 对抗审计无未解决结论
- 覆盖率盲点已列出且每项有处置（要么补用例、要么说明不测的理由）

最终输出汇总表：

```
| 策略 slug        | 用例数 | 杀死突变数 | 覆盖分支数 | 状态转移 | 状态     |
|-----------------|--------|-----------|-----------|----------|----------|
| equivalence_... | N      | N         | N         | N        | active   |
| property_based  | N      | N         | N         | N        | active   |
| contract_test   | N      | N         | N         | N        | active   |
| mutation_audit  | N      | N         | N         | N        | active   |
| ...             | ...    | ...       | ...       | ...      | ...      |

覆盖率盲点清单:
- <分支/状态转移> | 处置: <已补用例 / 不测理由>
- ...

未杀死突变最终清单（应为空或附理由）:
- <若有，附为什么不补用例的理由>

最终行:
GOAL_STATE: complete  或  GOAL_STATE: blocked_<reason>
```

# 硬性约束

- 不要跳过任何步骤
- 不要在没产出代码用例的情况下输出"应该测这些场景"
- 不要让"对抗审计"变成橡皮图章——必须找具体反例或具体未杀死突变
- 不要把行覆盖率当完成，必须追踪变异分数与状态转移覆盖
- 不要混用策略思路（每条用例严格属于一个家族）
- 模糊措辞禁止清单：应该没问题 / 看起来够 / 常规覆盖 / 标准做法 / 大概覆盖
- 如果某条策略确实不适用本对象，标记 `not_applicable_<reason>` 并补一条替代策略

现在开始第 1 步。
````

## 可选增强

- **Python 项目**：让 LLM 在第 2 步同时输出 `pytest` + Hypothesis 的混合代码，变异测试配合 `mutmut` 跑真值校验。
- **API 项目**：在第 1 步前加一段 OpenAPI / 接口契约文档原文，让 LLM 据此自动派生 `contract_test` 家族。
- **半自动循环**：跑完一轮后，把 LLM 输出的代码 + 元数据真跑一遍 Stryker / mutmut，把变异分数回填给 LLM 做第 6 轮（"针对真实未杀死突变再补一轮"）——这就把单会话模板升级为半自动循环。

## 模板设计要点

- **角色切换**：用 `[以 /xxx 身份]` 模拟多代理，强迫 LLM 在不同视角间切换，避免向单一思路收敛。
- **元数据强制**：每个用例必须写"杀死什么突变、覆盖什么分支、保护什么状态转移"——把"经过代码"和"验证行为"分开。
- **对抗审计是橡皮图章的风险**：模板明确禁止"应该没问题"等措辞，要求返回 5 类结论之一，且"通过"必须附逐用例验证。
- **GOAL_STATE 终行**：模仿 Crouzeix 项目的 `tools.update_goal({status:"complete"})` 机制，没有这行任务不算完成。
- **blocked 也是一种合法结果**：如果盲点无法补全，输出 `GOAL_STATE: blocked_<reason>` 而不是假装完成——这正是 Crouzeix 项目"诚实标记阻塞"原则的体现。
