# 多代理测试审计器

> 派生自 Crouzeix 猜想项目的多代理对抗式方法论：13 线程 / 9,173 推理摘要 / 1,379 数值实验 / 三次独立端到端审计。本技能把该方法论映射到软件测试领域，把"数学证明"换成"测试用例集 + 变异分数报告 + 覆盖率报告"，把"对抗审计"换成"变异测试 + 盲点扫描 + 人审 PR"。

## 何时使用

当任务同时满足下列全部条件时调用：

- **复杂测试场景**：不是单接口 happy path 验证，而是需要多视角、多形态、多攻击面的综合测试设计。
- **可量化交付物**：输出必须是可执行的测试用例集 + 可读的变异分数/覆盖率报告，而非"测试方案描述"。
- **缺陷代价高**：错误会造成实际损失（资金、数据、安全、合规），值得花数小时迭代。
- **可接受多轮对抗**：以小时计的迭代式测试设计，而非秒级单次执行。

典型适用场景：
- 核心业务流程的回归测试套件设计（如支付、风控、订单状态机）
- API 契约测试 + 集成边界审计
- 安全测试（注入、越权、重放、SSRF、供应链）
- 性能 / 压力测试场景设计
- 测试套件债务清理与盲点审计
- 缺陷根因分析（多假设并存、对抗证伪）

不要用于：
- 简单 CRUD 单元测试
- 已有明确测试矩阵的回归脚本维护
- 仅 happy path 验证
- 一次性脚本验证 / 冒烟测试

## 核心哲学（不可协商）

1. **多样化策略家族优先。** 启动时即配备 ≥4 条**实质**不同的测试策略（等价类/边界值、属性测试、契约测试、变异测试、状态机模型测试、混沌工程、性能形态、攻击面分析）。不允许"用例措辞不同但思路相同"冒充多样性。

2. **保护早期独立性。** 不要告诉大多数测试代理当前倾向的策略。让它们独立设计用例，再交叉。若所有代理都收敛到"管理员路径覆盖"，即视为独立性测试失败。

3. **维护显式测试策略注册表。** 按测试**思想**分组，而非按用例措辞。若多代理收敛到同一家族，把部分重定向到探索不充分的家族。

4. **拒绝覆盖率垄断。** "行覆盖 100%"不等于"测得好"。一条路线若最终只能证明"代码被执行过"而非"行为正确"，**不算接近完成**。变异分数、契约覆盖率、状态迁移覆盖率必须并行追踪。

5. **诚实标记阻塞。** 当一条策略（如 E2E 太慢、混沌场景无法稳定复现）停滞时，标记 `blocked`。只有当引入新机制（如录制回放、流量回放、Service Mesh 注入）时才重开。

6. **对抗审计贯穿全程。** 每个用例集都必须接受：变异测试（机器审，找未杀死突变）+ 覆盖率盲点扫描 + 人审 PR（找语义缺口）。对抗代理必须返回**具体反例 / 具体未杀死突变 / 具体未覆盖分支 / 具体缺失边界**。拒绝"看起来够" / "覆盖很高了" / "应该没问题"。

7. **仅在完整后返回。** 不要因当前策略失败或盲点太多就提前结束。启动新一轮、引入新策略家族、重审已删除的用例。**只有当完成闸门全部通过且 ≥3 次独立审计签字时**才返回。

## 工作流程

### 第 0 轮 —— 设置（根代理 / 测试 Owner）

1. 写下**待测对象的契约**：API 规格、状态转移图、性能基线、安全要求、合规约束。固定其版本（git commit / SHA-256）。
2. 初始化**测试策略注册表**（模板见下），行为空。
3. 定义完成闸门（见下"完成闸门"段）。
4. 设定预算：默认每轮 4 小时 / 30 万 token，可扩展至 12 小时 / 100 万 token。

### 第 1 轮 —— 策略组合启动

启动 ≥4 个直接子代理，每个分配到注册表中**不同**的家族。路径命名：`/suite/<family_slug>`。

示例家族：
- `equivalence_boundary`（等价类 + 边界值）
- `property_based`（Hypothesis / fast-check 属性测试）
- `contract_test`（Pact 契约测试）
- `mutation_test`（Stryker / mutmut 反向驱动）
- `state_model`（AltWalker 模型测试）
- `fuzz_chaos`（模糊测试 + Chaos Mesh）
- `perf_profile`（性能 / 压力形态）
- `attack_surface`（安全攻击面分析）

对每个子代理，根代理的派发消息**必须**：
- 仅陈述被测契约与交付格式（可执行测试代码 + 变异分数 / 覆盖率报告）。
- **不**披露根代理当前倾向的策略。
- 要求返回**具体用例 + 能杀死的突变类型 + 覆盖的具体分支/状态转移**——拒绝"已覆盖边界"等模糊陈述。
- 禁止"应该没问题" / "标准做法" / "常规覆盖"等含糊措辞。

### 第 2..N 轮 —— 综合、质疑、重定向

每轮结束后，根代理：

1. **综合**：从每个存活代理收集用例集与报告；更新策略注册表。
2. **质疑**：对每个用例集，派发**对抗审计代理**（独立），从三方面审计：
   - **变异审计**：跑 Stryker / mutmut，列出未杀死的突变，反推缺失用例。
   - **覆盖率盲点扫描**：跑代码 + 分支 + 状态覆盖，列出未覆盖的分支与未触发的状态转移。
   - **语义审计**：人审 PR，针对每个用例问"删掉它哪个突变会存活 / 哪个分支会失去保护"。
3. **重定向**：
   - 若 ≥3 个代理收敛到同一家族（如都堆在路径覆盖），杀掉重复者，重派到探索不充分的家族（如属性测试、混沌、契约）。
   - 若策略 `blocked`（如 E2E 太慢、混沌场景无法稳定复现），保持阻塞，要求新机制才重开。
   - 若策略报告"覆盖率已 100%"但变异分数低于阈值，标记 `blocked_elegance`——拒绝把覆盖率当完成。
4. **派生二级子代理**：当某直接子代理报告了一个有前景的子机制（如"用流量回放重建真实用户路径"）时：`/suite/<family_slug>/<sub_mechanism>`。
5. **允许且鼓励晚启动**：后期才补的策略（如混沌测试、变异测试后补）可能反而找到根因 bug，别过早关停。Crouzeix 案例中最终赢家正是最后启动的路线。
6. **交叉授粉**仅在独立代理充分发展后进行——避免早期互相污染收敛。

### 终轮 —— 完成性测试

一个测试套件只有当**下列全部**满足时才算完成：

- (a) 全部用例在 CI 中通过，无随机失败（flaky 必须 ≥0.5% 阈值之内）。
- (b) **覆盖率闸门**：行覆盖 ≥ 85%、分支覆盖 ≥ 75%、状态转移覆盖 ≥ 90%（按待测对象调整）。
- (c) **变异分数闸门**：Stryker / mutmut 全量跑，分数 ≥ 80%。
- (d) **静态扫描闸门**：SonarQube / Semgrep / Snyk 零 critical，高严重度 ≤ 阈值。
- (e) **性能基线闸门**：P95 / P99 / 错误率未退化超过基线阈值。
- (f) **审计签字**：≥3 个独立审计者（不是用例作者）签字，每份审计引用具体突变/分支/反例验证。
- (g) **目标状态**：CI pipeline 显式 `GOAL_STATE: complete`，否则不允许合并。

## 测试策略注册表（模板）

根代理全程维护此表，每轮后更新。

```
| 家族 slug            | 核心思想（≤30 字）                | 状态               | 负责代理路径                          | 阻塞原因 / 拒绝理由                                          |
|----------------------|-----------------------------------|--------------------|----------------------------------------|------------------------------------------------------------------|
| equivalence_boundary | 等价类划分 + 边界值扫描           | active             | /suite/equivalence_boundary            | —                                                                |
| property_based       | Hypothesis 找不变式               | active             | /suite/property_based                  | —                                                                |
| contract_test        | Pact 消费者驱动契约             | active             | /suite/contract_test                    | —                                                                |
| mutation_test        | Stryker 反向驱动盲点             | active             | /suite/mutation_test                    | —                                                                |
| state_model         | AltWalker 状态机模型测试         | blocked            | /suite/state_model                     | E2E 太慢阻塞，待引入流量回放再重开                              |
| fuzz_chaos          | 模糊测试 + Chaos Mesh            | active             | /suite/fuzz_chaos                       | —                                                                |
| perf_profile        | 阶梯 + 脉冲 + 雪崩负载           | active             | /suite/perf_profile                     | —                                                                |
| attack_surface      | 注入 / 越权 / SSRF / 重放        | active             | /suite/attack_surface                   | —                                                                |
| ...                  | ...                               | ...                | ...                                     | ...                                                              |
```

状态取值：`active` | `blocked` | `blocked_elegance` | `supporting` | `superseded` | `winner`。

`blocked_elegance` 用于标记"看起来高覆盖但变异分数低"的策略——拒绝把覆盖率当完成。

## 测试套件路径式命名

把每个用例按"套件 / 子域 / 功能 / 场景"四层组织，便于审计与注册表对齐：

```
/suite/api_contract/user_login/edge_case_empty_pwd
/suite/state_model/order/refund_double_click
/suite/perf_profile/payment_gateway/cache_stampede
/suite/attack_surface/admin_panel/idor_user_id_swap
```

每个路径节点对应注册表中的一条策略或场景，便于在审计日志中精确引用。

## 对抗审计清单

对每个用例集，对抗审计代理**必须**返回下列之一：

- 一个**未杀死的突变**（含突变位置、突变类型、为什么现存用例无法发现）。
- 一个**未覆盖的分支/状态转移**（含源码行号或状态图转移编号）。
- 一个**具体反例**（输入参数 + 期望行为 + 实际行为 + 复现脚本）。
- 一个**契约缺口**（消费者期望未被覆盖的契约字段）。
- 一次**无条件通过**（含逐用例验证：每个用例杀死哪些突变、覆盖哪些分支、保护哪些状态转移）。

禁止的审计输出（视为无效，重新派发新审计代理）：
- "覆盖很高了"
- "看起来够"
- "应该没问题"
- "标准做法"
- "常规覆盖足够"
- 任何没有具体突变/分支/反例的状态报告。

## 计算合理性闸门（终轮前强制）

宣布完成前，必须跑：

- **变异测试全量**：Stryker / mutmut，记录变异分数、未杀死突变清单。
- **随机 fuzz ≥600 次**：Hypothesis / 自定义 fuzzer，记录发现的失败输入与最小化复现。
- **覆盖率盲点扫描**：行 + 分支 + 状态转移，对比设计文档列出未触达的合法状态。
- **性能基线对比**：与上一基线的 P50/P95/P99/错误率对比，退化超过阈值即拒绝。
- **静态扫描**：SonarQube / Semgrep / Snyk 全量扫描，critical 必须 0。

所有报告写入交付物审计日志。任一闸门未过 → 回到第 2..N 轮。

## 输出契约

最终交付物**必须**包含以下全部：

1. **测试用例集**：可执行代码（pytest / jest / Stryker 配置等），CI 中跑全绿、无 flaky。
2. **变异分数报告**：Stryker / mutmut 全量输出，未杀死突变清单 + 反推补丁用例。
3. **覆盖率报告**：行/分支/状态转移覆盖率，未覆盖项清单 + 处置说明（不测也要说明理由）。
4. **盲点审计日志**：每次对抗审计一行，含审计代理身份、被审对象、结论（未杀死突变 / 未覆盖分支 / 反例 / 契约缺口 / 通过）、具体引用。
5. **测试策略注册表快照**：最终状态表，显示赢家策略与被阻塞/拒绝的备选，各附一句理由。
6. **计算合理性报告**：fuzz 脚本、变异测试日志、性能基线对比、静态扫描报告。
7. **目标状态**：CI pipeline 末尾输出字面行 `GOAL_STATE: complete`，否则不允许合并。在没有 CI 的场景，根测试 Owner 显式在交付物最后一行写下该字面行。

## 单会话 LLM 简化用法（无需多代理框架）

在普通 LLM 对话中也能用，关键是**强迫多视角 + 对抗自审**：

**测试设计五步法**

```
1. 列出 ≥4 条实质不同的测试策略（不是用例，是策略）
2. 每条策略各产 5-10 个用例，注明它能杀死的突变类型与覆盖的分支
3. 跑变异测试（Stryker / mutmut）找未杀死的突变
4. 让 LLM 以"对抗审计代理"角色，针对未杀死突变反推新用例
5. 完成闸门：覆盖率 + 变异分数 + 静态扫描 + 至少 3 个用例被另一人评审签字
```

模拟多代理角色切换示例：

```
[以 /suite/equivalence_boundary 身份]：先用等价类划分登录输入域...
[以 /suite/property_based 身份]：找不变式"任意合法输入下重试次数 ≤ N"...
[以 /suite/mutation_test 身份]：先跑 Stryker 看哪些突变未杀死...
[以 /suite/attack_surface 身份]：从越权角度切入，关注 user_id 交换...
[以对抗审计代理身份]：上面用例集未杀死 login.py:42 的 ≤→< 突变，反推新用例...
```

## 反模式（显式禁止）

- ❌ 把行覆盖率 100% 当成完成。
- ❌ 把"happy path 通过"当成完成。
- ❌ 让用例作者当自己的审计者。
- ❌ 跳过变异测试就宣布完成。
- ❌ 不告诉子代理倾向策略 → 实际上却把倾向写进了 prompt。
- ❌ 因变异分数低就降低阈值而非补用例。
- ❌ flaky 测试置之不理就合入。
- ❌ 性能基线退化未触发闸门。
- ❌ 静态扫描 critical 未清零就合入。
- ❌ 用户要可执行测试代码却返回测试方案描述。

## 资源与失败模式说明

- **规模预期**：复杂业务流程的完整测试套件审计可能需要数小时与数十万 token。据此规划；不要在 2 轮后就因"够多了"中止。
- **覆盖率陷阱**：行覆盖 ≥ 90% 但变异分数 ≤ 60% 是常见信号——说明用例"经过"了代码但没"验证"行为。这是注册表中"blocked_elegance"的典型触发条件。
- **flaky 反复**：如果一条 E2E 用例 flaky，不要降低阈值，标记 `blocked` 并要求新机制（流量回放 / 隔离环境 / 服务虚拟化）才重开。
- **晚启动策略可能胜出**：变异测试和混沌测试经常在后期才暴露根因 bug，不要在前期就否定它们。

## 与 multi-agent-research-prover 的差异

| 维度 | research-prover（数学/算法） | test-auditor（软件测试） |
|---|---|---|
| 交付物 | 可编译 LaTeX / Lean 证明 | 可执行测试代码 + 报告 |
| 多样化家族 | 解析 / 几何 / 代数 / 极值… | 等价类 / 属性 / 契约 / 变异… |
| 对抗代理 | 找 gaps / conditionals / 循环 | 找未杀死突变 / 未覆盖分支 / 反例 |
| 计算闸门 | 小规模随机数值验证 | 变异测试 + fuzz + 性能基线 |
| 完成判定 | 编译 + 三次独立审计 | 全绿 + 变异分数 + 覆盖率 + 性能 + 三次签字 |
| 路径式命名 | /root/hardy_duality_route | /suite/api_contract/user_login/edge |

## 溯源

本技能派生自 Crouzeix 猜想项目展示的多代理对抗式方法论（13 线程 / 9,173 推理摘要 / 1,379 数值实验 / 14h50m / 194 万 token / 三次独立端到端审计）。把"对抗式证明开发"映射为"对抗式测试设计"，把"对抗代理找 gaps"映射为"变异测试找未杀死突变 + 人审找语义盲点"。它是对该方法论的泛化，**不**构成对软件质量的绝对保证。原项目在创建本技能时形式化同行评审仍在进行；本技能产出的测试套件同样适用该标准——独立人审与 CI 闸门不可省略。
