# 性能指标详解

本指南详细解释性能测试中的各种指标，帮助您理解和分析测试结果。

---

## 一、核心指标详解

### 1.1 TPS（Transactions Per Second）

**定义**：每秒完成的事务数，衡量系统吞吐量。

**计算公式**：
```
TPS = 总事务数 / 测试持续时间（秒）
```

**示例**：
```
测试持续时间：600秒（10分钟）
总事务数：480,000

TPS = 480,000 / 600 = 800 TPS
```

**目标设置建议**：

| 系统类型 | 推荐TPS目标 | 说明 |
|---------|------------|------|
| 内部管理系统 | < 100 TPS | 低并发场景 |
| 普通电商网站 | 100-500 TPS | 中等并发 |
| 热门电商网站 | 500-2000 TPS | 高并发 |
| 大型互联网应用 | 2000+ TPS | 超高并发 |

**如何优化TPS**：
1. 减少单次请求处理时间
2. 增加并发线程数（注意不要超过系统极限）
3. 优化数据库查询
4. 使用缓存减少数据库压力

### 1.2 响应时间（Response Time）

**定义**：从发送请求到收到响应的时间。

**单位**：毫秒（ms）

**常见百分位指标**：

| 指标 | 说明 | 目标值建议 |
|------|------|-----------|
| **平均响应时间** | 所有请求的平均时间 | < 目标值 |
| **中位数（50%）** | 50%请求的响应时间 | < 目标值 |
| **90% Line** | 90%请求的响应时间 | < 目标值 |
| **95% Line** | 95%请求的响应时间 | < 目标值 |
| **99% Line** | 99%请求的响应时间 | < 目标值×2 |

**为什么关注百分位**：

```
假设有100个请求的响应时间：
- 90个请求：100ms（正常）
- 9个请求：500ms（较慢）
- 1个请求：5000ms（很慢）

平均响应时间 = (90×100 + 9×500 + 1×5000) / 100 = 145ms
95% Line = 500ms
99% Line = 5000ms

结论：平均值很好，但实际有5%的用户体验很差！
```

**响应时间目标建议**：

| 用户体验 | P95响应时间 | 说明 |
|---------|------------|------|
| 极速 | < 100ms | 如搜索引擎 |
| 快速 | 100-300ms | 如普通查询 |
| 正常 | 300-800ms | 如复杂计算 |
| 可接受 | 800-2000ms | 如报表生成 |
| 较差 | > 2000ms | 用户会感到卡顿 |

### 1.3 错误率（Error Rate）

**定义**：失败请求占总请求的比例。

**计算公式**：
```
错误率 = 失败请求数 / 总请求数 × 100%
```

**示例**：
```
总请求数：10,000
失败请求数：25

错误率 = 25 / 10,000 × 100% = 0.25%
```

**错误率目标建议**：

| 场景 | 目标错误率 | 说明 |
|------|-----------|------|
| 生产环境 | < 0.1% | 严格要求 |
| 测试环境 | < 0.5% | 标准要求 |
| 预发布 | < 1% | 宽松要求 |

**常见错误类型**：

| 错误类型 | HTTP状态码 | 可能原因 |
|---------|-----------|---------|
| 客户端错误 | 400 | 参数错误 |
| 认证错误 | 401 | Token过期/无效 |
| 权限错误 | 403 | 无权限访问 |
| 资源不存在 | 404 | URL错误 |
| 服务器错误 | 500 | 程序异常 |
| 服务不可用 | 503 | 服务器过载 |
| 超时错误 | - | 响应超时 |

### 1.4 吞吐量（Throughput）

**定义**：单位时间内处理的数据量。

**单位**：KB/sec、MB/sec

**分类**：
- **接收吞吐量**：从服务器接收的数据速率
- **发送吞吐量**：发送到服务器的数据速率

**影响因素**：
- 网络带宽
- 数据压缩
- 响应体大小

## 二、指标关系分析

### 2.1 TPS与响应时间的关系

**理想状态**：
```
TPS ↑ 且 响应时间 ↓ = 系统性能优秀
```

**常见关系模式**：

#### 模式1：线性增长（健康）
```
TPS
 ↑
 │   ╱
 │  ╱
 │ ╱
 │╱
 └────────→ 线程数
     响应时间平稳
```

**说明**：随着线程数增加，TPS线性增长，响应时间保持稳定。

**结论**：系统还有优化空间，可以继续增加并发。

#### 模式2：拐点出现（接近极限）
```
TPS
 ↑
 │    ╱╲
 │   ╱  ╲
 │  ╱    ╲
 │ ╱      ╲
 └─────────→ 线程数
         ↑
        拐点
```

**说明**：到达某个点后，TPS不再增长，响应时间开始激增。

**结论**：这是系统的最佳并发点，超过后性能下降。

#### 模式3：性能下降（过载）
```
TPS
 ↑
 │    ╱╲
 │   ╱  ╲
 │  ╱    ╲
 │ ╱      ╲____
 └─────────────→ 线程数
         ↑    ↑
        拐点  响应时间爆炸
```

**说明**：继续增加线程，TPS下降，响应时间急剧增加。

**结论**：系统已过载，需要减少并发或优化系统。

### 2.2 如何找到最佳并发点

**方法**：阶梯式压力测试

**步骤**：
```
阶梯1: 50线程  → 记录TPS和响应时间
阶梯2: 100线程 → 记录TPS和响应时间
阶梯3: 200线程 → 记录TPS和响应时间
阶梯4: 400线程 → 记录TPS和响应时间
阶梯5: 600线程 → 记录TPS和响应时间
```

**分析**：
```
找到满足以下条件的最大线程数：
1. TPS达到目标值
2. P95响应时间 < 目标值
3. 错误率 < 目标值
```

| 列名 | 英文 | 说明 |
|------|------|------|
| 标签 | Label | 请求名称 |

| 平均值 | Average | 平均响应时间(ms) |
| 中位数 | Median | 50%请求响应时间(ms) |
| 90%百分位 | 90% Line | 90%请求响应时间(ms) |
| 95%百分位 | 95% Line | 95%请求响应时间(ms) |
| 99%百分位 | 99% Line | 99%请求响应时间(ms) |
| 最小值 | Min | 最小响应时间(ms) |
| 最大值 | Max | 最大响应时间(ms) |
| 异常% | Error% | 错误率(%) |
| 吞吐量 | Throughput | 每秒请求数 |
| 接收KB/sec | Received KB/sec | 接收数据速率 |
| 发送KB/sec | Sent KB/sec | 发送数据速率 |

### 3.2 聚合报告分析示例

**示例报告**：
```
Label                    #Samples  Average   Median   90%Line   95%Line   99%Line   Min    Max    Error%  Throughput  Received KB/sec  Sent KB/sec
用户登录                    10000     156       120       200       280       500      50    1200     0.12%    832.5        156.3            45.2
获取商品列表                10000      85        70       120       150       300      30     800     0.05%   1176.5        892.1            32.8
添加购物车                  10000     220       180       300       420       650      80    1500     0.28%    454.5        234.5            67.3
查看购物车                  10000      95        80       130       170       350      40    1000     0.08%   1052.6        456.2            28.5
TOTAL                      40000     139       105       180       260       550      30    1500     0.13%   3515.6       1739.1           173.8
```

**分析**：

| 接口 | 状态 | 分析 |
|------|------|------|
| 用户登录 | ⚠️ 需要关注 | P99=500ms，有长尾效应 |
| 获取商品列表 | ✅ 优秀 | 各项指标都很好 |
| 添加购物车 | 🔴 需优化 | P95=420ms，TPS最低 |
| 查看购物车 | ✅ 良好 | 指标正常 |
| **整体** | ✅ 通过 | TPS=3515，P95=260ms，错误率0.13% |

**建议**：
1. 重点优化"添加购物车"接口
2. 关注"用户登录"的长尾请求
3. 整体性能达标，可以上线

### 3.3 健康检查清单

每次测试后，检查以下项目：

```
✅ TPS是否达到目标？
✅ P95响应时间是否在目标内？
✅ P99响应时间是否可接受？
✅ 错误率是否低于阈值？
✅ 响应时间是否稳定（波动小）？
✅ 各个接口的表现是否均衡？
✅ 是否有明显的瓶颈接口？
```

## 五、性能瓶颈定位

### 5.1 常见瓶颈类型

#### 瓶颈1：CPU瓶颈

**现象**：
- TPS不再增长
- 响应时间开始增加
- 服务器CPU使用率 > 90%

**定位方法**：
```bash
# Linux
top -p <进程ID>

# Windows
任务管理器 -> 性能 -> CPU
```

**可能原因**：
- 代码中有大量计算
- 正则表达式复杂
- 序列化/反序列化开销大
- 无索引的排序操作

**解决方案**：
- 优化算法复杂度
- 使用缓存
- 添加数据库索引
- 代码Review

#### 瓶颈2：内存瓶颈

**现象**：
- TPS波动大
- 频繁Full GC
- 内存使用率持续增长

**定位方法**：
```bash
# 查看JVM内存使用
jstat -gcutil <PID> 1000

# 查看内存快照
jmap -dump:format=b,file=heap.hprof <PID>
```

**可能原因**：
- 内存泄漏
- 大对象未释放
- 缓存使用不当
- 线程数过多

**解决方案**：
- 修复内存泄漏
- 调整JVM参数
- 优化缓存策略
- 减少线程数

#### 瓶颈3：数据库瓶颈

**现象**：
- TPS上不去
- 响应时间慢
- 数据库连接池耗尽

**定位方法**：
```sql
-- 查看慢查询
SHOW PROCESSLIST;

-- 查看表锁
SHOW OPEN TABLES WHERE In_use > 0;

-- 查看索引使用情况
EXPLAIN SELECT * FROM table WHERE ...;
```

**可能原因**：
- 缺少索引
- 锁等待
- 连接池不足
- SQL语句效率低

**解决方案**：
- 添加/优化索引
- 优化SQL语句
- 增加连接池大小
- 读写分离

#### 瓶颈4：网络瓶颈

**现象**：
- 吞吐量达到上限
- 响应时间包含大量网络延迟
- 带宽使用率接近100%

**定位方法**：
```bash
# Linux
iftop
nload

# Windows
任务管理器 -> 性能 -> 网络
```

**可能原因**：
- 响应体过大
- 大文件上传下载
- 网络带宽不足
- 跨区域延迟

**解决方案**：
- 启用数据压缩
- 使用CDN
- 减少响应体大小
- 选择更近的机房

### 5.2 排查流程

```
性能问题
    │
    ├─ 检查服务器资源
    │   ├─ CPU > 90%? → CPU瓶颈
    │   ├─ 内存 > 80%? → 内存瓶颈
    │   └─ 磁盘I/O > 70%? → 磁盘瓶颈
    │
    ├─ 检查数据库
    │   ├─ 慢查询? → SQL优化
    │   ├─ 锁等待? → 事务优化
    │   └─ 连接池满? → 增加连接数
    │
    ├─ 检查网络
    │   ├─ 带宽满? → 压缩/CDN
    │   └─ 延迟高? → 就近部署
    │
    └─ 检查应用代码
        ├─ 计算密集? → 优化算法
        ├─ 内存泄漏? → 修复泄漏
        └─ 同步阻塞? → 异步化
```

## 六、性能目标设定

### 6.1 如何设定合理目标

**方法1：基于历史数据**
```
如果历史数据：
- 高峰期TPS：500
- P95响应时间：300ms
- 错误率：0.1%

设定目标：
- TPS ≥ 600（20%增长）
- P95响应时间 ≤ 400ms（预留缓冲）
- 错误率 ≤ 0.5%
```

**方法2：基于业务需求**
```
业务需求：
- 日活用户：10万
- 高峰期并发率：10%
- 每个用户平均操作数：5

计算：
并发用户 = 10万 × 10% = 1万
目标TPS = 1万 × 5 / 3600 ≈ 14（保守）
实际设定：TPS ≥ 50（留有余量）
```

**方法3：基于竞品对比**
```
竞品指标：
- TPS：800
- P95响应时间：400ms
- 错误率：0.2%

设定目标：
- TPS ≥ 1000（超过竞品）
- P95响应时间 ≤ 300ms（更快）
- 错误率 ≤ 0.1%（更稳定）
```

### 6.2 目标设定模板

```
性能测试目标
============

一、测试目标
- 测试日期：YYYY-MM-DD
- 测试环境：测试环境/预发布/生产
- 测试类型：基准测试/负载测试/压力测试

二、性能指标
| 指标 | 目标值 | 警告阈值 | 失败阈值 |
|------|--------|---------|---------|
| TPS | ≥ 800 | < 700 | < 500 |
| P95响应时间 | ≤ 500ms | > 600ms | > 1000ms |
| 错误率 | < 0.5% | > 1% | > 5% |
| CPU使用率 | < 70% | > 80% | > 95% |
| 内存使用率 | < 80% | > 85% | > 95% |

三、测试场景
1. 基准测试：5线程，20次循环
2. 负载测试：100线程，持续10分钟
3. 压力测试：阶梯式增加到500线程

四、通过标准
- 所有指标达到目标值
- 无严重错误
- 系统稳定运行
```
