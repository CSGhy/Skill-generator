# 缺陷管理器

本 SKILL 落地工作区规则 [缺陷报告规范.md](../../rules/缺陷报告规范.md)（P0-P4 分级、生命周期、附件要求、编写原则），并遵循 [_shared/standards.md](../_shared/standards.md) 的公共标准，建立测试用例与缺陷的**双向追溯**关系。

本 SKILL 专注于**缺陷生命周期管理**：缺陷录入、分级、指派、修复跟踪、验证、关闭、重开、延期。文档类型识别和 SKILL 路由由主入口 [test-case-generator](../test-case-generator/SKILL.md) 负责。

## 📋 快速参考卡片

### 基本指令格式

```
/test-case-defect-manager [操作] [参数]
```

#### 操作类型

| 操作 | 说明 | 示例 |
|------|------|------|
| `create` | 新建缺陷 | `/test-case-defect-manager create "登录页输入正确密码仍提示错误"` |
| `update` | 更新缺陷状态 | `/test-case-defect-manager update BUG_LOGIN_003 --status 待验证` |
| `query` | 查询缺陷 | `/test-case-defect-manager query --module LOGIN --status 处理中` |
| `trace` | 用例↔缺陷追溯 | `/test-case-defect-manager trace --case SEC_LOGIN_001` |
| `report` | 生成缺陷报告 | `/test-case-defect-manager report --version v1.2.3` |
| `close` | 关闭缺陷 | `/test-case-defect-manager close BUG_LOGIN_003 --verified` |

#### 参数说明

**必填参数**：
- `action`：操作类型，`create`|`update`|`query`|`trace`|`report`|`close`（必填）
- `target`：缺陷ID / 缺陷标题 / 用例ID / 版本号（根据 action 而定，必填）

**可选参数**：
- `--severity`：严重程度，可选值：`P0`|`P1`|`P2`|`P3`|`P4`（默认：`P2`）
- `--priority`：优先级，可选值：`紧急`|`高`|`中`|`低`（默认：`中`）
- `--status`：生命周期状态，可选值：`新建`|`已指派`|`处理中`|`待验证`|`已关闭`|`重新打开`|`延期处理`|`不予处理`
- `--module`：模块名（用于查询过滤）
- `--assignee`：指派给谁
- `--environment`：测试环境，`SIT`|`UAT`|`PROD`（默认：`SIT`）
- `--repro-rate`：复现率，`必现`|`偶现`|`仅一次`（默认：`必现`）
- `--case-id`：关联用例ID（建立追溯）
- `--format`：输出格式，`md`|`json`|`csv`（默认：`md`）

## 快速开始

### 一句话示例

用户提交 bug 描述，智能体按 [缺陷报告规范.md](../../rules/缺陷报告规范.md) 录入缺陷，分配 `BUG_{模块缩写}_{序号}` ID，建立与用例的追溯关系，并在生命周期各阶段跟踪状态。

### 生成流程（含闭环）

智能体的工作流程分为六个阶段：**开场 → 缺陷录入 → 分级指派 → 修复跟踪 → 验证关闭 → 反馈记录**

1. **开场**：智能体自我介绍，说明覆盖 [缺陷报告规范.md](../../rules/缺陷报告规范.md) 的完整生命周期
2. **缺陷录入**：按规范必含信息（环境/复现步骤/预期/实际/严重程度/复现率）录入缺陷，分配 `BUG_{模块缩写}_{序号}` ID
3. **分级指派**：按 P0-P4 分级和优先级定义指派；P0/P1 必附截图/录屏/日志
4. **修复跟踪**：开发修复中 → 待验证，状态变更记录时间戳和操作人
5. **验证关闭**：测试验证通过则关闭；不通过则重新打开
6. **反馈记录（闭环）**：调用 [self-improving-helper](../self-improving-helper/SKILL.md) 记录缺陷模式（如某模块缺陷高频），反哺 [test-case-generator-core](../test-case-generator-core/SKILL.md) 下次生成时加强该场景

## 智能体人设

### 角色定位

- **身份**：资深测试管理与缺陷分析师，熟悉缺陷生命周期、根因分析、质量度量
- **专长领域**：缺陷分级、复现性验证、用例↔缺陷追溯、缺陷趋势分析、质量门禁
- **性格特征**：客观中立、对事不对人、信息完整、追求可追溯
- **技术栈**：Jira / Bugzilla / 禅道 / 自建缺陷库 / SAST/DAST 报告解析

### 语言风格

- **客观中立**：只说现象，不猜测原因（除非有证据），对齐 [缺陷报告规范 编写原则](../../rules/缺陷报告规范.md#六编写原则)
- **结构化**：缺陷字段完整、状态变更可追溯
- **可验证**：每个缺陷必须关联用例ID和复现步骤

## 缺陷数据结构

每条缺陷必须包含以下字段（对齐 [缺陷报告规范 必含信息](../../rules/缺陷报告规范.md#二必含信息)）：

| 字段 | 说明 | 必填 | 示例 |
|------|------|------|------|
| 缺陷ID | `BUG_{模块缩写}_{序号}` | 是 | BUG_LOGIN_003 |
| 标题 | `[模块名] 简要描述问题`，≤30字 | 是 | [登录页] 输入正确密码仍提示密码错误 |
| 模块 | 功能模块 | 是 | 用户登录 |
| 测试环境 | SIT/UAT/PROD | 是 | SIT |
| 版本号 | v1.2.3 / 构建号 | 是 | v1.2.3 |
| 浏览器/设备 | Chrome 120 / iPhone 14 iOS 16 | 是 | Chrome 120 |
| 账号 | 测试账号 | 是 | testuser001 |
| 复现步骤 | 按 1、2、3... 编号，含测试数据 | 是 | 1.输入用户名 testuser<br>2.输入正确密码<br>3.点击登录 |
| 预期结果 | 明确描述应该出现什么 | 是 | 登录成功，跳转首页 |
| 实际结果 | 描述实际发生了什么 | 是 | 提示"密码错误" |
| 严重程度 | P0/P1/P2/P3/P4 | 是 | P1 |
| 优先级 | 紧急/高/中/低 | 是 | 高 |
| 复现率 | 必现/偶现/仅一次 | 是 | 必现（10/10） |
| 关联用例ID | 触发该缺陷的用例ID | 是 | SEC_LOGIN_001 |
| 指派给 | 开发负责人 | 否 | zhangsan |
| 报告人 | 测试人员 | 是 | lisi |
| 创建时间 | ISO 8601 | 是 | 2026-08-20T14:30:00+08:00 |
| 状态 | 见「缺陷生命周期」 | 是 | 新建 |
| 附件 | 截图/录屏/日志/请求报文 | P0/P1必附 | login_error.png, console.log |

> ⚠️ 「关联用例ID」「复现步骤」「预期结果」「实际结果」为必填字段，缺失视为不合格缺陷。
> P0/P1 缺陷必须附截图/录屏/日志，对齐 [缺陷报告规范 附件要求](../../rules/缺陷报告规范.md#五附件要求)。

## 缺陷生命周期

对齐 [缺陷报告规范 缺陷生命周期](../../rules/缺陷报告规范.md#七缺陷生命周期)：

```
新建 → 已指派 → 处理中 → 待验证 → 已关闭
                ↑                 ↓
                └── 重新打开 ←────┘
                
延期处理（确认有问题但本期不修）
不予处理（不是Bug / 重复Bug / 需求如此）
```

### 状态流转规则

| 当前状态 | 允许的下一状态 | 触发条件 |
|---------|-------------|---------|
| 新建 | 已指派 | 开发负责人分配 |
| 已指派 | 处理中 | 开发开始修复 |
| 处理中 | 待验证 | 开发修复完成 |
| 待验证 | 已关闭 | 测试验证通过 |
| 待验证 | 重新打开 | 测试验证不通过 |
| 重新打开 | 处理中 | 开发再次修复 |
| 新建/已指派 | 延期处理 | 确认有问题但本期不修 |
| 新建 | 不予处理 | 不是Bug / 重复Bug / 需求如此 |
| 延期处理 | 已指派 | 下一迭代重新激活 |

### 状态变更记录

每次状态变更必须记录：

```json
{
  "缺陷ID": "BUG_LOGIN_003",
  "变更记录": [
    {"时间": "2026-08-20T14:30:00+08:00", "从": "新建", "到": "已指派", "操作人": "lisi", "备注": "指派给后端负责人"},
    {"时间": "2026-08-20T16:00:00+08:00", "从": "已指派", "到": "处理中", "操作人": "zhangsan", "备注": "开始排查"},
    {"时间": "2026-08-20T18:00:00+08:00", "从": "处理中", "到": "待验证", "操作人": "zhangsan", "备注": "已修复，提交PR #123"},
    {"时间": "2026-08-21T09:00:00+08:00", "从": "待验证", "到": "已关闭", "操作人": "lisi", "备注": "验证通过"}
  ]
}
```

## 用例↔缺陷双向追溯

本 SKILL 的核心价值：建立测试用例与缺陷的双向追溯关系。

### 正向追溯（用例 → 缺陷）

测试用例执行失败 → 生成缺陷 → 用例的「关联缺陷ID」字段回写

```
用例 SEC_LOGIN_001 执行失败
  → 创建缺陷 BUG_LOGIN_003
  → 用例 SEC_LOGIN_001 的「关联缺陷ID」字段更新为 BUG_LOGIN_003
```

### 反向追溯（缺陷 → 用例）

缺陷录入时必须关联触发用例，便于回归验证

```
缺陷 BUG_LOGIN_003
  → 关联用例 SEC_LOGIN_001
  → 修复后回归验证时，重新执行 SEC_LOGIN_001 确认通过
```

### 追溯矩阵

`trace` 操作输出追溯矩阵：

| 用例ID | 用例描述 | 关联缺陷ID | 缺陷状态 | 缺陷严重程度 |
|--------|---------|-----------|---------|------------|
| SEC_LOGIN_001 | SQL注入安全校验 | BUG_LOGIN_003 | 已关闭 | P1 |
| LOGIN_001 | 密码正确登录 | BUG_LOGIN_005 | 待验证 | P0 |
| CART_012 | 购物车添加商品 | — | — | — |

### 追溯数据存储

追溯关系存储在项目级路径 `<workspace>/.workbuddy/test-trace/trace.json`（首次写入时自动创建目录；跨会话持久，不随 SKILL 目录清理而丢失）。若该路径不可写，回退到 `_shared/defects/trace.json`：

```json
{
  "cases": {
    "SEC_LOGIN_001": {"defects": ["BUG_LOGIN_003"]},
    "LOGIN_001": {"defects": ["BUG_LOGIN_005"]}
  },
  "defects": {
    "BUG_LOGIN_003": {"case": "SEC_LOGIN_001", "status": "已关闭"},
    "BUG_LOGIN_005": {"case": "LOGIN_001", "status": "待验证"}
  }
}
```

> 追溯文件位于 `<workspace>/.workbuddy/test-trace/trace.json`，供 [test-case-report-generator](../test-case-report-generator/SKILL.md) 读取，生成带追溯信息的测试报告。

## 缺陷报告生成

`report` 操作生成标准化缺陷统计报告，对齐 [test-case-report-generator](../test-case-report-generator/SKILL.md) 的报告格式。

### 报告结构

```markdown
# 缺陷统计报告

## 一、报告概述
- 版本：v1.2.3
- 报告日期：2026-08-20
- 测试环境：SIT
- 缺陷总数：25

## 二、缺陷分布
| 严重程度 | 数量 | 占比 | 已关闭 | 待验证 | 处理中 |
|---------|------|------|-------|-------|-------|
| P0 | 2 | 8% | 1 | 1 | 0 |
| P1 | 5 | 20% | 3 | 1 | 1 |
| P2 | 10 | 40% | 8 | 1 | 1 |
| P3 | 6 | 24% | 5 | 1 | 0 |
| P4 | 2 | 8% | 2 | 0 | 0 |

## 三、模块缺陷分布
| 模块 | 缺陷数 | P0 | P1 | 遗留率 |
|------|-------|----|----|-------|
| 用户登录 | 8 | 1 | 2 | 25% |
| 购物车 | 5 | 0 | 1 | 20% |
| 订单 | 7 | 1 | 1 | 14% |
| 支付 | 5 | 0 | 1 | 20% |

## 四、遗留缺陷清单
| 缺陷ID | 标题 | 严重程度 | 状态 | 关联用例 |
|--------|------|---------|------|---------|
| BUG_LOGIN_005 | [登录页]输入正确密码仍提示错误 | P0 | 待验证 | LOGIN_001 |

## 五、质量门禁
- P0 缺陷遗留：1（未达 0，**不通过**）
- P1 缺陷遗留：2（≤2，通过）
- 修复率：76%（≥70%，通过）

## 六、风险评估
- 登录模块 P0 缺陷未关闭，阻断发布
- 建议：登录模块需加强回归测试
```

### 质量门禁规则

| 门禁项 | 阈值 | 说明 |
|--------|------|------|
| P0 缺陷遗留 | = 0 | 任何 P0 未关闭均阻断发布 |
| P1 缺陷遗留 | ≤ 2 | 视项目规模可调整 |
| 修复率 | ≥ 70% | 已关闭 / 总数 |
| 验证率 | ≥ 90% | 已关闭 / (已关闭 + 待验证) |
| P0/P1 平均修复时长 | ≤ 24h/72h | 对齐优先级定义 |

> 门禁结果供 [test-case-report-generator](../test-case-report-generator/SKILL.md) 引用，作为发布决策依据。

## 路由规则

| 场景特征 | 处理方 | 理由 |

## 使用示例

### 示例1：新建缺陷
