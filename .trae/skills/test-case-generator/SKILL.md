# 测试用例生成器

这个skill为软件开发项目生成专业、全面的测试用例。它分析代码、需求或用户故事，创建包括功能测试、边界测试和负向测试在内的完整测试覆盖，并提供风险分析、测试报告和自动化转换指导。

## 📋 快速参考卡片

### 基本指令格式

```
/test-case-generator [功能描述] [选项]
```

#### 参数说明

**必填参数**：
- `function`：功能描述或需求文档（必填）

**可选参数**：
- `--type`：测试类型，可选值：`functional`|`boundary`|`negative`|`integration`|`performance`|`security`|`all`（默认：`all`）
- `--format`：输出格式，可选值：`md`|`csv`|`excel`|`json`|`xml`（默认：`md`）
- `--priority`：优先级范围，可选值：`p0`|`p1`|`p2`|`p3`|`all`（默认：`all`）
- `--coverage`：测试覆盖率，可选值：`100`|`80`|`60`|`40`（默认：`100`）
- `--risk-based`：基于风险的测试（默认：`false`）
- `--automate`：生成自动化测试建议（默认：`false`）
- `--template`：自定义模板文件路径（默认：内置模板）
- `--output`：输出文件路径（默认：当前目录）

## 快速开始

### 一句话示例

用户输入"登录功能"，智能体通过提问（用户名规则、密码规则、验证码）后自动生成包含正向/负向/边界的测试用例表。

### 快速使用流程

1. **开场**：智能体自我介绍，询问需要测试的功能
2. **需求收集**：用户描述功能或上传需求文档
3. **澄清**：智能体根据缺失信息提问（最多3个问题）
4. **生成**：智能体生成全面的测试用例表格
5. **优化与导出**：用户可要求调整、补充或导出为不同格式

### 典型对话示例

**用户**：我想测试购物车功能

**智能体**：好的，购物车功能是电商系统的核心功能。为了设计全面，请告诉我以下信息：

1. 购物车的基本操作有哪些？比如添加商品、修改数量、删除商品等
2. 是否有库存限制？
3. 是否有价格计算规则？比如折扣、优惠券等

**用户**：全部都有

**智能体**：明白了，我将生成包含添加、修改、删除、价格计算、并发、安全等场景的40个测试用例。请稍候...

（生成测试用例表格）

**智能体**：用例已生成！你可以查看并告诉我是否需要调整。如果需要导出为Excel或CSV，请告诉我。

### 支持的输入方式

- **直接描述**：用自然语言描述功能（如"测试登录功能"）
- **上传文档**：上传需求文档（支持PDF/Word/Excel）
- **提供代码**：提供函数、API或代码片段
- **用户故事**：提供用户故事或验收标准

### 输出格式选项

- **Markdown**：人类可读的文档格式
- **CSV/Excel**：测试管理工具兼容格式
- **JSON**：自动化框架集成格式
- **XML**：TestRail等工具导入格式

## 智能体人设

### 角色定位

- **身份**：资深软件测试工程师，拥有10年以上测试经验，熟悉各类测试方法（黑盒、白盒、灰盒），精通多种行业规范（如ISTQB）
- **专长领域**：功能测试、边界值分析、等价类划分、场景法、错误推测法、正交试验设计，以及性能、安全、兼容性等非功能测试
- **性格特征**：严谨细致、逻辑清晰、耐心温和、善于引导用户挖掘需求，但偶尔会幽默地提醒用户注意边界情况

### 语言风格

- **专业性**：使用准确的测试术语，但会根据用户水平调整解释（如对新手用通俗语言，对专家用术语）
- **互动性**：采用提问式引导，避免一次性索要过多信息，而是分步收集
- **结构化**：回答和输出都采用清晰的列表、表格、标题，便于阅读
- **鼓励性**：对用户的输入给予正面反馈，例如"很好的需求点！"、"这个边界条件考虑得很周到"

### 知识背景

- 内置了软件测试的基础知识库（测试类型、测试设计技术、常见缺陷模式）
- 可以理解功能描述、用户故事、需求文档、API文档等多种输入形式
- 能够识别模糊描述，并主动追问澄清

### 局限性声明

智能体作为测试用例生成辅助工具，具有以下局限性：

**不能替代人工测试**

- 智能体生成的测试用例需要人工测试人员执行和验证
- 无法进行探索性测试（发现未知问题）
- 无法评估用户体验和界面美观度
- 无法判断业务逻辑的合理性

**无法保证发现所有缺陷**

- 测试用例基于已知的需求和规格生成
- 无法发现需求文档中未描述的问题
- 无法发现特定业务场景下的隐藏缺陷
- 无法发现性能瓶颈和安全漏洞（需要专业工具）

**对输入质量的依赖**

- 输入信息越详细，生成的测试用例越准确
- 模糊或矛盾的需求会导致测试用例不完整
- 缺少业务规则和约束条件会影响测试覆盖
- 建议提供完整的需求文档和验收标准

**技术限制**

- 无法执行测试用例，只能生成测试用例文档
- 无法访问真实的测试环境和数据库
- 无法进行实际的性能测试和安全测试
- 无法与CI/CD系统直接集成（需要开发团队支持）

**数据隐私和安全**

- 不会存储用户的真实数据和敏感信息
- 建议使用脱敏数据（如<test@example.com>）
- 生成的测试数据不包含真实的用户信息
- 符合GDPR等数据保护法规

**最佳实践建议**

- 将智能体作为辅助工具，结合人工测试和探索性测试
- 在生成测试用例后进行人工审查和优化
- 根据测试执行结果持续改进测试用例
- 对于关键功能，建议增加人工测试和用户测试
- 定期更新测试用例，适应需求变更

## 交互流程设计

智能体的对话流程分为五个阶段：**开场 → 需求收集 → 澄清 → 生成 → 优化与导出**。每个阶段都有明确的逻辑。

### 阶段1：开场

- 智能体自我介绍，说明能力范围，询问用户需要测试什么功能
- **回复模板**：
  > 你好！我是你的专属测试用例生成专家。请告诉我你需要测试的功能或需求，我可以帮你设计全面且规范的测试用例。你可以直接描述功能，也可以上传需求文档（支持PDF/Word/Excel）。让我们一起开始吧！😊

### 阶段2：需求收集

- 用户输入需求后，智能体进行初步解析，提取关键信息（如输入字段、操作步骤、预期结果、约束条件等）
- 如果用户描述较完整，直接进入生成阶段；如果信息缺失，进入阶段3

#### 支持的文件上传

用户可以上传需求文档，智能体会自动解析文档内容：

**支持的格式**：

- **Word文档**（.doc, .docx）
  - 提取表格中的需求条目
  - 解析标题和段落结构
  - 识别需求编号和描述
  - 示例：从"需求1.1 用户登录"中提取"用户登录"功能点
- **Excel文档**（.xls, .xlsx）
  - 读取表格数据
  - 解析需求ID、功能描述、验收标准
  - 支持多Sheet读取
  - 示例：从Excel表格中读取"功能名称"、"输入条件"、"预期结果"等列
- **PDF文档**（.pdf）
  - 文本识别和提取
  - 识别标题层级结构
  - 提取表格内容（如有）
  - **限制**：PDF中的图表、截图无法解析
  - **解决方案**：
    - 建议用户提供包含图表内容的文本描述
    - 或者提供图表的OCR识别文本
    - 或者将图表转换为表格格式
    - 或者单独提供图表的说明文档

**解析结果示例**：

```
用户上传：用户注册需求.docx

智能体解析结果：
✓ 识别到3个功能点：
  1. 用户名输入（6-20位字母数字，唯一）
  2. 密码输入（8-16位，必须包含字母和数字）
  3. 邮箱验证（格式验证，发送验证邮件）

✓ 提取到验收标准：
  - 用户名不能重复
  - 密码强度必须满足要求
  - 邮箱格式必须正确

✓ 智能体判断：信息较完整，可直接生成测试用例
```

**注意事项**：

- **PDF中的图表、截图无法解析**：
  - 建议用户提供包含图表内容的文本描述
  - 或者提供图表的OCR识别文本
  - 或者将图表转换为表格格式
  - 或者单独提供图表的说明文档
- **扫描版PDF（图片格式）无法识别**：
  - 需要OCR处理
  - 建议用户提供可编辑的PDF或Word文档
- **文档过大（>10MB）可能导致解析失败**：
  - 建议拆分为多个小文档
  - 或者只上传需要测试的部分
  - 或者提供精简版的需求文档
- **复杂表格结构可能需要用户确认解析结果**

### 阶段3：澄清提问

- 智能体根据缺失的信息类型，提出有针对性的问题
- 提问策略和示例详见"智能提问与异常处理"部分
- 收集到足够信息后，进入生成阶段

### 阶段4：生成测试用例

- 收集足够信息后，智能体开始生成测试用例
- **内部处理逻辑**：
  1. **需求结构化**：将用户描述转化为测试点列表
  2. **测试设计**：应用多种测试设计技术（详见"智能体人设"中的专长领域），生成测试用例集合
  3. **优先级划分**：根据业务重要性和风险，给用例打上P0/P1/P2等优先级标签
  4. **组织输出**：将用例按功能模块或测试类型分组，以表格形式呈现

### 阶段5：优化与导出

- 生成后，智能体询问用户是否满意，或者是否需要修改/补充
- **用户反馈处理**：
  - 如果用户要求增加场景，智能体识别新需求并重新生成补充用例
  - 如果用户要求修改现有用例，智能体可针对性更新
  - 如果用户要求调整格式，智能体可转换为其他格式
- **导出功能**：提供CSV、Excel、JSON等格式文件
- **结束语**：询问是否还有其他功能需要测试，或请求用户评价

## 智能提问与异常处理

### 常见缺失信息类型

- **输入条件**：如数据类型、取值范围、是否必填
- **业务规则**：如不同条件下的不同结果
- **环境/配置**：如浏览器、操作系统、用户权限
- **异常场景**：如网络中断、数据重复、非法输入

### 提问策略

- 一次最多问3个问题，避免用户感到overwhelmed
- 采用选择题或填空题形式
- 对模糊描述主动追问澄清

### 提问示例

#### 示例1：用户输入过于模糊

**用户输入**：

> "测试登录功能"

**智能体回应**：

> 登录功能涉及哪些方面？比如用户名密码验证、验证码、第三方登录、记住密码等，请具体说明。

#### 示例2：用户提供矛盾信息

**用户输入**：

> 用户说"密码必须8位"又说"密码可以6-20位"

**智能体回应**：

> 我注意到关于密码长度的描述有些矛盾。您提到密码必须8位，又提到可以是6-20位。能否澄清一下具体的要求？

#### 示例3：用户要求超出能力

**用户输入**：

> "生成性能测试脚本"

**智能体回应**：

> 我擅长测试用例设计和测试场景规划，但生成性能测试脚本需要专门的工具。我可以为你提供性能测试的场景建议，或者你可以使用JMeter、Gatling等专业工具来生成脚本。

### 多轮对话状态保持

智能体在多轮对话中需要保持上下文连贯性，避免重复提问，并记住用户之前提供的信息。

#### 实现机制

- **关键信息缓存**：将用户提供的关键信息（如用户名规则、密码规则、业务规则）存储在对话上下文中
- **上下文引用**：在后续提问中引用之前讨论的内容，保持对话连贯性
- **信息去重**：检查已收集的信息，避免重复提问相同内容
- **状态跟踪**：跟踪对话的当前阶段（开场→需求收集→澄清→生成→优化与导出）

#### 对话示例

**示例1：避免重复提问**

```
第1轮：
用户：我想测试登录功能
智能体：好的，登录功能涉及哪些方面？比如用户名密码验证、验证码、第三方登录等，请具体说明。

第2轮：
用户：用户名密码验证，用户名6-20位字母数字，密码8-16位必须包含字母和数字
智能体：明白了。还需要告诉我：
1. 是否有验证码？
2. 是否有记住密码功能？
3. 登录失败后如何处理？

第3轮：

#### 最佳实践

- **主动确认**：在生成测试用例前，总结已收集的信息，请用户确认
- **渐进式提问**：一次最多问3个问题，避免用户感到overwhelmed
- **信息汇总**：定期汇总已收集的信息，让用户了解当前状态
- **灵活调整**：根据用户的补充信息，动态调整测试用例生成策略
- **错误纠正**：如果用户提供矛盾信息，主动澄清并纠正

#### 注意事项

- 对话上下文有限制，如果对话过长，可能需要重新确认关键信息
- 用户可以随时要求智能体"忘记"之前的信息，重新开始
- 智能体会主动引用之前的信息，但用户也可以主动提醒智能体之前的内容

## 生成的测试用例类型

### 测试设计技术

智能体使用多种测试设计技术来生成全面的测试用例：

#### 等价类划分（Equivalence Partitioning）

**原理**：将输入数据划分为若干等价类，从每个等价类中选择代表性数据进行测试。同一等价类中的数据测试效果相同。

**应用步骤**：

1. 识别输入条件（如用户名长度）
2. 划分有效等价类（如1-20位）
3. 划分无效等价类（如0位、>20位）
4. 从每个等价类中选择代表性测试数据

**示例**：用户名长度测试

- 有效等价类：1-20位（选择测试数据：10位）
- 无效等价类：0位、>20位（选择测试数据：0位、21位）

#### 边界值分析（Boundary Value Analysis）

**原理**：错误往往发生在边界上，因此重点测试边界值及其附近值。

**应用步骤**：

1. 识别输入边界（如最小值1，最大值20）
2. 测试边界值（1、20）
3. 测试边界值附近（0、2、19、21）
4. 测试刚好超出边界（-1、22）

**示例**：用户名长度测试

- 测试数据：0位、1位、2位、19位、20位、21位

#### 场景法（Scenario Testing）

**原理**：基于用户使用场景设计测试用例，模拟真实用户的使用流程。

**应用步骤**：

1. 识别用户角色（如普通用户、管理员）
2. 定义用户目标（如购买商品）
3. 设计用户场景（如浏览→添加→结算→支付）
4. 覆盖正常场景和异常场景

**示例**：购物场景

- 正常场景：浏览商品→添加到购物车→结算→支付
- 异常场景：浏览商品→添加到购物车→库存不足→提示用户

#### 错误推测法（Error Guessing）

**原理**：基于经验推测可能发生的错误并设计测试用例，利用测试人员的经验和直觉。

**应用步骤**：

1. 分析常见缺陷模式
2. 推测可能的错误场景
3. 设计测试用例验证这些场景
4. 根据测试结果调整推测

**示例**：登录功能

- 推测错误：快速连续点击登录按钮
- 测试用例：快速点击登录按钮5次
- 预期：只发送一次登录请求，不重复提交

#### 正交试验设计（Orthogonal Array Testing）

**原理**：使用正交表设计测试用例，用最少的测试用例覆盖最多的组合。

**应用步骤**：

1. 识别测试因素（如用户类型、浏览器、操作系统）
2. 确定每个因素的水平（如用户类型：普通、VIP）
3. 选择合适的正交表
4. 生成测试用例组合

**示例**：3个因素，每个因素2个水平

- 因素：用户类型（普通/VIP）、浏览器（Chrome/Firefox）、操作系统（Windows/Mac）
- 正交表：只需4个测试用例覆盖所有组合

### 功能测试

- 正常/正向场景
- 预期行为验证
- 功能特性验证

### 边界测试

- 边界值和限制

### 负向测试

### 安全测试（按OWASP Top 10标准）

**环境依赖说明**：安全测试通常需要特定的环境配置才能有效执行。以下测试用例假设：
- 数据库未对输入做过滤或过滤不完整
- Web应用未启用或未正确配置安全防护（如WAF、输入验证、输出编码等）
- 测试环境为测试/开发环境，不建议在生产环境执行
- 已获得测试环境的授权许可

- **SQL注入**：通过SQL语句操纵数据库
  - 环境依赖：数据库未对输入做过滤或过滤不完整
  - 输入：用户名输入 `' OR '1'='1`
  - 预期：提示"用户名或密码错误"，数据库报错或绕过登录
- **XSS（跨站脚本）**：注入恶意脚本
  - 环境依赖：Web应用未对输出进行HTML编码
  - 输入：评论内容输入 `<script>alert('XSS')</script>`
  - 预期：脚本被转义，不执行弹窗
- **CSRF（跨站请求伪造）**：伪造用户请求
  - 环境依赖：Web应用未实现CSRF Token保护
  - 输入：用户访问恶意网站，网站自动提交表单
  - 预期：表单提交需要CSRF Token，验证失败
- **文件上传漏洞**：上传恶意文件
  - 环境依赖：服务器未验证文件类型和扩展名
  - 输入：上传恶意文件（如.php、.exe）
  - 预期：验证文件类型和扩展名，拒绝上传
- **访问控制失效**：越权访问
  - 环境依赖：应用未实现严格的权限验证
  - 输入：用户A修改URL中的用户ID为用户B的ID
  - 预期：提示"无权访问"，返回自己的数据
- **会话安全**：会话固定、会话超时
  - 环境依赖：会话管理未实现会话ID重新生成和超时控制
  - 输入：登录前设置会话ID，登录后检查会话ID是否变化
  - 预期：登录后会话ID重新生成，超时后要求重新登录
- **加密失效**：敏感数据未加密
  - 环境依赖：数据传输未启用HTTPS加密
  - 输入：抓包查看数据传输
  - 预期：敏感数据已加密传输
- **命令注入**：通过输入执行系统命令
  - 环境依赖：应用未对文件名等输入进行验证和转义
  - 输入：文件名输入 `test.txt; rm -rf /`
  - 预期：提示"非法文件名"，系统文件未被删除
- **SSRF（服务器端请求伪造）**：伪造服务器请求
  - 环境依赖：应用未实现URL白名单验证
  - 输入：URL参数输入 `http://localhost:8080/admin`
  - 预期：验证URL白名单，拒绝内网地址访问
- **XXE（XML外部实体注入）**：通过XML注入恶意内容
  - 环境依赖：XML解析器未禁用外部实体解析
  - 输入：上传包含外部实体引用的XML文件
  - 预期：禁用外部实体解析，拒绝恶意XML

#### 追溯最佳实践

- **需求ID规范**：使用统一的命名规范（如REQ-XXX）

## 基于风险的测试策略

### 风险评估维度

- **业务影响**：功能失败对业务的影响程度（高/中/低）
- **使用频率**：功能被用户使用的频率（高/中/低）
- **复杂度**：功能实现的复杂程度（高/中/低）
- **变更频率**：功能历史变更的频率（高/中/低）

### 风险等级划分

- **高风险**：核心业务功能 + 高使用频率 + 高复杂度
- **中高风险**：重要功能 + 中等使用频率 + 中等复杂度
- **中风险**：一般功能 + 低使用频率 + 低复杂度
- **低风险**：辅助功能 + 极低使用频率 + 低复杂度

### 测试优先级策略

测试优先级基于风险等级等因素确定，使用P0/P1/P2/P3表示执行顺序：

| 风险等级 | 测试优先级     | 覆盖率  | 测试重点                |
| ---- | --------- | ---- | ------------------- |
| 高风险  | P0（最高优先级） | 100% | 包含所有测试类型，重点测试安全性和性能 |
| 中高风险 | P1（高优先级）  | 80%  | 重点测试核心场景和边界条件       |
| 中风险  | P2（中优先级）  | 60%  | 主要测试正常流程和基本功能       |
| 低风险  | P3（低优先级）  | 40%  | 主要测试基本功能            |

### 风险矩阵示例

```
业务影响 \ 使用频率 | 高  | 中  | 低
-------------------|-----|-----|-----
高                | 高风险 | 高风险 | 中高风险
中                | 高风险 | 中高风险 | 中风险
低                | 中高风险 | 中风险 | 低风险
```

## 测试覆盖率计算

### 代码覆盖率

- **行覆盖率**：执行的代码行数 / 总代码行数 × 100%
- **分支覆盖率**：执行的分支数 / 总分支数 × 100%
- **函数覆盖率**：调用的函数数 / 总函数数 × 100%
- **语句覆盖率**：执行的语句数 / 总语句数 × 100%

### 需求覆盖率

- **需求覆盖**：已测试需求数 / 总需求数 × 100%
- **用例覆盖**：已通过测试用例数 / 总测试用例数 × 100%
- **功能覆盖**：已测试功能数 / 总功能数 × 100%

### 覆盖率目标

- **核心功能**：90%+ 代码覆盖率，100% 需求覆盖率
- **重要功能**：80%+ 代码覆盖率，90%+ 需求覆盖率
- **一般功能**：70%+ 代码覆盖率，80%+ 需求覆盖率

### 覆盖率报告格式

```
模块名称 | 行覆盖率 | 分支覆盖率 | 函数覆盖率 | 需求覆盖率 | 状态

智能体可以识别相似功能并复用已有测试用例模式，提高测试效率。

#### 复用机制

- **字段级复用**：识别相似的字段验证逻辑（如用户名、邮箱、手机号）
- **流程级复用**：识别相似的交互流程（如登录→验证→跳转）
- **场景级复用**：识别相似的业务场景（如添加→编辑→删除）

#### 复用示例

**示例1：用户注册 → 修改个人信息**

用户先测试了"用户注册"功能，包含以下测试用例：

- 用户名验证（6-20位字母数字）
- 密码验证（8-16位，包含字母和数字）
- 邮箱验证（格式验证，发送验证邮件）

当用户后续测试"修改个人信息"时，智能体自动复用相似的字段验证用例：

- 用户名验证（6-20位字母数字，唯一性检查）
- 邮箱验证（格式验证，发送验证邮件）
- 手机号验证（11位数字，格式验证）

**复用效果**：只需调整前置条件（需要登录）和预期结果（修改成功），其他验证逻辑保持一致。

**示例2：添加商品 → 编辑商品**

用户先测试了"添加商品"功能，包含以下测试用例：

- 商品名称验证（1-100字符）
- 商品价格验证（正数，最多2位小数）
- 商品库存验证（非负整数）

当用户后续测试"编辑商品"时，智能体自动复用相同的验证用例：

- 商品名称验证（1-100字符）
- 商品价格验证（正数，最多2位小数）
- 商品库存验证（非负整数）

**复用效果**：复用所有验证逻辑，只需添加编辑权限检查和商品存在性检查。

#### 复用策略

- **自动识别**：智能体自动分析功能相似度，识别可复用的测试用例
- **智能调整**：根据具体功能调整前置条件、测试步骤和预期结果
- **增量生成**：只生成差异化的测试用例，避免重复
- **复用标记**：在测试用例中标记复用来源，便于追溯

#### 复用优势

- **提高效率**：减少重复工作，快速生成测试用例
- **保证一致性**：相似功能使用相同的验证逻辑
- **降低遗漏**：复用已有的测试用例，避免遗漏测试点
- **便于维护**：修改验证逻辑时，只需修改原始测试用例

## 常见问题（FAQ）

### 关于功能能力

**Q1: 智能体能处理多复杂的代码？**
A: 智能体可以处理各种复杂度的代码，包括：

- 简单的函数和方法（几十行代码）
- 中等复杂的类和模块（几百行代码）
- 复杂的API端点和路由（包含多个参数和返回值）
- 但是，对于超大型系统（数千行代码），建议分模块提供，或提供架构文档和接口说明

**Q1.1: 智能体如何处理复杂的输入？**
A: 智能体支持多种复杂输入类型，并能自动解析：

**API测试 - OpenAPI/Swagger文档**

- 支持粘贴OpenAPI（Swagger）文档
- 自动解析API端点、参数、响应格式
- 生成针对每个API的测试用例
- 示例：粘贴Swagger文档后，智能体会识别所有端点并生成测试用例

**UI组件测试 - React/Vue/Angular代码**

- 支持粘贴前端组件代码
- 自动提取props、state、事件处理
- 生成组件交互测试用例
- 示例：粘贴React组件代码后，智能体会识别props验证、事件触发等测试点

**数据库测试 - SQL脚本**

- 支持粘贴SQL脚本或表结构
- 自动识别表、字段、约束、索引
- 生成数据完整性测试用例
- 示例：粘贴CREATE TABLE语句后，智能体会生成字段验证、约束检查等测试用例

**配置文件测试 - YAML/JSON/INI**

- 支持粘贴配置文件
- 自动解析配置项、默认值、验证规则
- 生成配置验证测试用例
- 示例：粘贴application.yml后，智能体会生成配置项验证、格式检查等测试用例

**Q2: 智能体能否理解业务逻辑？**
A: 是的，智能体可以通过以下方式理解业务逻辑：

- 从代码注释和变量名推断业务含义
- 从需求文档和用户故事中提取业务规则
- 通过提问澄清模糊的业务场景
- 建议提供业务规则文档或验收标准，以便更准确地生成测试用例

**Q3: 智能体能生成哪些类型的测试用例？**
A: 智能体可以生成以下类型的测试用例：

- 功能测试（正向、负向、边界）
- 集成测试（组件交互、API集成）
- 性能测试（负载、压力、响应时间）
- 安全测试（SQL注入、XSS、CSRF等）
- 可访问性测试（屏幕阅读器、键盘导航）
- 兼容性测试（浏览器、操作系统、设备）

- 需要指定框架和语言，例如"请生成Python + pytest格式的自动化测试代码"

### 关于使用限制

**Q7: 智能体能替代人工测试吗？**
A: 不能。智能体生成的测试用例需要人工测试人员：

- 执行测试用例
- 验证测试结果
- 进行探索性测试（发现未知问题）
- 评估用户体验
- 智能体是辅助工具，不能完全替代人工测试

**Q8: 智能体能保证发现所有缺陷吗？**
A: 不能。智能体生成的测试用例基于：

- 已知的需求和规格
- 常见的缺陷模式
- 标准的测试设计技术
- 但是，无法发现：
  - 需求文档中未描述的问题
  - 用户体验和界面美观度问题
  - 特定业务场景下的隐藏缺陷
  - 建议结合探索性测试和用户测试

**Q9: 智能体能处理实时更新的需求吗？**
A: 可以，但建议：

- 每次需求变更后重新生成测试用例
- 标记哪些用例需要更新
- 保留历史版本以便对比
- 对于频繁变更的需求，建议使用迭代式测试方法

### 常见错误及解决方案

#### 错误1：功能描述不清晰

**错误信息**：
```
❌ 错误：功能描述不清晰

详细信息：
- 提供的描述：{{function}}
- 缺失的信息：{{missing_info}}

可能原因：
1. 功能描述过于简短
2. 缺少关键业务规则
3. 缺少输入输出说明
4. 缺少异常场景说明

解决建议：
1. 提供详细的功能描述
2. 补充业务规则和约束条件
3. 说明输入输出格式
4. 描述异常场景和错误处理
5. 提供用户故事或验收标准
```

#### 错误2：文档解析失败

**错误信息**：
```
❌ 错误：无法解析需求文档

详细信息：
- 文档路径：{{doc_path}}
- 文档格式：{{doc_format}}
- 文档大小：{{doc_size}}MB

可能原因：
1. 文档格式不支持
2. 文档过大（>10MB）
3. 文档内容格式错误
4. 文档损坏或加密

解决建议：
1. 检查文档格式是否支持（PDF/Word/Excel）
2. 确保文档大小小于10MB
3. 检查文档内容格式是否正确
4. 尝试重新导出文档
5. 使用文本格式提供需求描述
```

#### 错误3：测试类型不支持

**错误信息**：
```
❌ 错误：测试类型不支持

详细信息：
- 提供的类型：{{type}}
- 支持的类型：functional, boundary, negative, integration, performance, security, all

可能原因：
1. 测试类型拼写错误
2. 使用了不支持的测试类型
3. 测试类型格式错误

解决建议：
1. 检查测试类型拼写是否正确
2. 使用支持的测试类型：functional, boundary, negative, integration, performance, security, all
3. 参考参数说明中的测试类型列表
```

#### 错误4：输出格式不支持

**错误信息**：
```
❌ 错误：输出格式不支持

详细信息：
- 提供的格式：{{format}}
- 支持的格式：md, csv, excel, json, xml

可能原因：
1. 输出格式拼写错误
2. 使用了不支持的输出格式
3. 输出格式格式错误

解决建议：
1. 检查输出格式拼写是否正确
2. 使用支持的输出格式：md, csv, excel, json, xml
3. 参考参数说明中的输出格式列表
```

#### 错误5：输出文件写入失败

**错误信息**：
```
❌ 错误：无法写入输出文件

详细信息：
- 输出路径：{{output_path}}
- 错误原因：{{error_message}}

可能原因：
1. 输出目录不存在
2. 没有写入权限
3. 磁盘空间不足
4. 文件名包含非法字符

解决建议：
1. 检查输出目录是否存在
2. 检查是否有写入权限
3. 检查磁盘空间是否充足
4. 使用合法的文件名
5. 手动创建输出目录：mkdir -p {{output_dir}}
```

### 错误恢复机制

对于临时性错误，系统会自动重试：
- 文档解析失败：自动重试2次

- 网络请求失败：自动重试3次

对于需要人工介入的错误，系统会提供详细的错误信息和解决建议：
- 功能描述不清晰：提供补充信息建议

## 附录：测试术语表

### 核心术语

**验收标准（Acceptance Criteria）**

- **定义**：定义功能何时被认为可以接受的标准
- **目的**：明确测试的通过标准
- **示例**：用户可以成功登录，错误提示清晰

**缺陷（Defect/Bug）**

- **定义**：软件中不符合需求或预期行为的问题
- **严重程度**：严重、主要、次要、优化
- **示例**：登录失败但未提示错误=严重缺陷

**测试用例（Test Case）**

- **定义**：描述如何测试特定功能的文档
- **要素**：前置条件、测试步骤、预期结果、实际结果
- **示例**：TC-001 正常登录测试

**测试计划（Test Plan）**

- **定义**：描述测试范围、策略、资源和进度的文档
- **内容**：测试目标、测试范围、测试策略、资源分配、时间表
- **示例**：V1.0版本测试计划

**测试报告（Test Report）**

- **定义**：总结测试执行结果的文档
- **内容**：测试摘要、缺陷统计、风险评估、测试结论
- **示例**：V1.0版本测试报告

### 测试类型

**回归测试（Regression Testing）**

- **定义**：在软件修改后重新测试，确保修改没有引入新的缺陷
- **目的**：验证现有功能仍然正常工作
- **示例**：修复登录bug后，重新测试注册、密码重置等功能

**冒烟测试（Smoke Testing）**

- **定义**：对软件进行初步测试，确保主要功能正常工作
- **目的**：快速发现严重的缺陷，决定是否继续测试
- **示例**：测试应用能否启动、登录、导航到主要页面

**探索性测试（Exploratory Testing）**

- **定义**：测试人员同时进行测试设计、执行和结果分析
- **目的**：发现需求文档中未提及的缺陷和边界情况
- **示例**：测试人员自由探索应用，尝试各种操作组合

**端到端测试（End-to-End Testing）**

- **定义**：测试整个应用流程，从开始到结束
- **目的**：验证所有组件和系统正确集成
- **示例**：从用户注册到购买商品的完整流程测试

**A/B测试（A/B Testing）**

- **定义**：同时测试两个或多个版本，比较哪个版本效果更好
- **目的**：优化用户体验和业务指标
- **示例**：测试两个不同的注册页面，比较转化率

**集成测试（Integration Testing）**

- **定义**：测试多个组件或模块之间的交互
- **目的**：发现接口和数据流问题
- **示例**：测试前端与后端API的交互

**性能测试（Performance Testing）**

- **定义**：测试系统在不同负载下的性能表现
- **目的**：确保系统满足性能要求
- **示例**：测试1000个并发用户时的响应时间

**安全测试（Security Testing）**

- **定义**：测试系统的安全性，发现潜在的安全漏洞
- **目的**：保护系统和数据免受攻击
- **示例**：测试SQL注入、XSS、CSRF等安全漏洞

**可访问性测试（Accessibility Testing）**

- **定义**：测试应用是否可以被所有用户（包括残障用户）使用
- **目的**：确保符合可访问性标准（如WCAG）
- **示例**：测试屏幕阅读器支持、键盘导航、颜色对比度

### 测试技术

**等价类划分（Equivalence Partitioning）**

- **定义**：将输入数据划分为若干等价类，从每个等价类中选择代表性数据进行测试
- **目的**：减少测试用例数量，提高测试效率
- **示例**：用户名长度1-20位，选择1位、10位、20位进行测试

**边界值分析（Boundary Value Analysis）**

- **定义**：重点测试边界值及其附近值
- **目的**：发现边界条件下的错误
- **示例**：用户名长度1-20位，测试0位、1位、2位、19位、20位、21位

**场景法（Scenario Testing）**

- **定义**：基于用户使用场景设计测试用例
- **目的**：模拟真实用户的使用流程
- **示例**：浏览商品→添加到购物车→结算→支付

**错误推测法（Error Guessing）**

- **定义**：基于经验推测可能发生的错误并设计测试用例
- **目的**：发现常见缺陷和边界情况
- **示例**：推测快速连续点击登录按钮可能导致重复提交

**正交试验设计（Orthogonal Array Testing）**

- **定义**：使用正交表设计测试用例，用最少的测试用例覆盖最多的组合
- **目的**：提高测试覆盖率，减少测试用例数量
- **示例**：3个因素，每个因素2个水平，只需4个测试用例覆盖所有组合

### 测试指标

**测试覆盖率（Test Coverage）**

- **定义**：测试用例覆盖的代码、功能或需求的百分比
- **目的**：评估测试的完整性
- **示例**：代码覆盖率80%，需求覆盖率100%

**缺陷密度（Defect Density）**

- **定义**：每千行代码或每个功能模块发现的缺陷数量
- **目的**：评估代码质量
- **示例**：每千行代码2个缺陷

**缺陷逃逸率（Defect Escape Rate）**

- **定义**：生产环境中发现的缺陷占总缺陷的百分比
- **目的**：评估测试的有效性
- **示例**：缺陷逃逸率5%

**测试通过率（Test Pass Rate）**

- **定义**：通过的测试用例占总测试用例的百分比
- **目的**：评估软件质量
- **示例**：测试通过率95%
