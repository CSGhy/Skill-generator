# 测试用例评审器

本 SKILL 遵循 [_shared/standards.md](../_shared/standards.md) 的公共标准，并对照工作区 [测试用例质量规范](../../rules/测试用例质量规范.md) 和 [测试金字塔原则](../../rules/测试金字塔原则.md) 进行评审。

这个skill专注于测试用例的评审和质量检查，提供全面的测试用例评审服务，包括完整性检查、正确性检查、可执行性检查、可维护性检查等。

## 📋 快速参考卡片

### 基本指令格式

```
/test-case-reviewer [测试用例] [选项]
```

#### 参数说明

**必填参数**：
- `test-cases`：待评审的测试用例（必填）

**可选参数**：
- `--review-type`：评审类型，可选值：`completeness`|`correctness`|`executability`|`maintainability`|`all`（默认：`all`）
- `--standard`：评审标准，可选值：`standard`|`strict`|`custom`（默认：`standard`）
- `--output-format`：输出格式，可选值：`md`|`json`|`csv`（默认：`md`）

#### 参数Schema

```json
{
  "test-cases": {
    "type": "string",
    "minLength": 1,
    "description": "待评审的测试用例"
  },
  "review-type": {
    "type": "string",
    "enum": ["completeness", "correctness", "executability", "maintainability", "all"],
    "default": "all",
    "description": "评审类型"
  },
  "standard": {
    "type": "string",
    "enum": ["standard", "strict", "custom"],
    "default": "standard",
    "description": "评审标准"
  },
  "output-format": {
    "type": "string",
    "enum": ["md", "json", "csv"],
    "default": "md",
    "description": "输出格式"
  }
}
```

### 常用命令

| 命令 | 说明 |
|------|------|
| "评审测试用例" | 评审测试用例质量 |
| "检查完整性" | 检查测试用例完整性 |
| "检查可执行性" | 检查测试用例可执行性 |
| "生成改进建议" | 生成改进建议 |

> 💡 **提示**：你可以直接粘贴测试用例，系统会按照评审标准进行全面的质量检查，并提供改进建议。例如："评审以下测试用例的质量"。

### 评审类型

| 评审类型 | 说明 | 检查项 |
|---------|------|--------|
| 完整性检查 | 检查测试用例是否覆盖所有需求 | 需求覆盖、场景覆盖、边界覆盖 |
| 正确性检查 | 检查测试用例是否正确 | 测试步骤、预期结果、数据正确性 |
| 可执行性检查 | 检查测试用例是否可执行 | 步骤清晰、前置条件、依赖关系 |
| 可维护性检查 | 检查测试用例是否易于维护 | 命名规范、结构清晰、复用性 |

## 评审检查清单

评审检查清单对照工作区 [测试用例质量规范](../../rules/测试用例质量规范.md) 和 [_shared/standards.md](../_shared/standards.md) 制定。

### 完整性检查

#### 5 类必覆盖场景（对照质量规范第四节）

- [ ] **正常场景**：主流程正向验证、常用数据组合是否有用例
- [ ] **边界值**：数值边界（最大/最小/0/空/null）、长度边界（最短/最长/为空）、集合边界（空集合/单元素/满容量）是否覆盖
- [ ] **等价类**：有效等价类（代表性数据）、无效等价类（各类非法输入）是否覆盖
- [ ] **异常场景**：网络异常/超时、依赖服务不可用、权限不足、数据冲突/重复提交、资源耗尽是否覆盖
- [ ] **兼容性**：不同浏览器/设备/操作系统、不同版本兼容、数据迁移兼容是否覆盖

#### 需求覆盖
- [ ] 所有功能需求都有对应的测试用例
- [ ] 所有非功能需求都有对应的测试用例
- [ ] 所有业务规则都有对应的测试用例
- [ ] 所有验收标准都有对应的测试用例

### 正确性检查

#### FIRST 原则（对照质量规范第二节）
- [ ] **Fast**：用例执行要快，避免不必要的等待和依赖
- [ ] **Independent**：用例之间互不依赖，可单独执行，执行顺序不影响结果
- [ ] **Repeatable**：多次执行结果一致，不依赖外部不稳定因素
- [ ] **Self-validating**：有明确的断言/预期结果，不需要人工判断
- [ ] **Timely**：需求确定后及时编写，与开发同步推进

#### 预期结果
- [ ] 预期结果明确具体，可验证
- [ ] 不使用「可能」「大概」「应该」等模糊表述
- [ ] 预期结果符合需求
- [ ] 预期结果无歧义（不说"正常显示"，要说"显示XX内容，字体14px，颜色#333"）

#### 数据正确性
- [ ] 测试数据符合业务规则
- [ ] 测试数据覆盖边界条件
- [ ] 测试数据包含异常数据
- [ ] 数据明确（不用"一些数据"、"若干条"，要说"3条数据"）

### 可执行性检查

#### 前置条件（对照质量规范第一节必含要素）
- [ ] 每条用例含「前置条件」字段（非空）
- [ ] 前置条件明确、可满足
- [ ] 前置条件完整、合理

#### 步骤清晰
- [ ] 测试步骤清晰明确，无歧义
- [ ] 测试步骤顺序正确
- [ ] 测试步骤无遗漏、无冗余
- [ ] 第三方也能照步骤执行

#### 依赖关系
- [ ] 依赖关系明确
- [ ] 依赖关系合理、可满足
- [ ] 依赖关系无循环
- [ ] 公用前置操作抽离为公共步骤/前置条件

#### 颗粒度（对照质量规范第三节）
- [ ] 一条用例只验证一个核心关注点
- [ ] 避免"超级用例"（一个用例覆盖N个功能点）

### 可维护性检查

#### ID 规范（对照 [_shared/standards.md](../_shared/standards.md#一用例-id-格式)）
- [ ] 用例 ID 格式符合 `{模块缩写}_{序号}`（如 LOGIN_001）
- [ ] API 用例 ID 格式符合 `API_{模块缩写}_{序号}`
- [ ] 不使用旧的纯数字格式（如 TC011001）
- [ ] ID 唯一无重复

#### 策略家族检查（对照 [_shared/standards.md](../_shared/standards.md#五-b测试策略家族与测试类型正交)）
- [ ] 每条用例含「策略家族」字段（值为枚举之一，含 manual_heuristic 兜底）
- [ ] 每批用例至少覆盖 4 条实质不同的策略家族
- [ ] 不存在"用例措辞不同但思路相同"冒充多样性
- [ ] 兜底家族 `manual_heuristic` 用例不超过总用例数 20%
- [ ] 每条 `manual_heuristic` 用例注明了无法匹配前 8 条家族的理由
- [ ] 复杂场景下填写了「能杀死的突变类型」「覆盖的分支」「保护的状态转移」元数据

#### 命名规范（对照质量规范第五节）
- [ ] 测试场景字段符合 `模块_功能点_场景_预期结果` 格式
- [ ] 用例名称清晰、统一、无歧义

#### 结构清晰
- [ ] 测试用例结构清晰
- [ ] 测试用例分组合理
- [ ] 测试用例层次分明
- [ ] 测试用例易于查找

#### 复用性
- [ ] 测试用例可复用
- [ ] 测试步骤可复用
- [ ] 测试数据可复用
- [ ] 测试用例可参数化

### 合规性检查（对照测试金字塔原则）

#### 金字塔比例（对照 [测试金字塔原则](../../rules/测试金字塔原则.md)）
- [ ] 每条用例标注了「测试层级」字段（unit/integration/e2e）
- [ ] unit 用例占比 ≥ 50%（目标 70%）
- [ ] integration 用例占比约 20%
- [ ] e2e 用例占比 ≤ 15%（目标 10%），且只测 P0 核心主流程
- [ ] 不存在「倒金字塔」（上层测试比下层多）
- [ ] 不存在「只有 E2E」的冰淇淋蛋筒模式

#### 测试前移
- [ ] 是否有单元测试覆盖核心逻辑
- [ ] 边界值、异常分支是否在单元层测试（而非推到 E2E）

### 对抗审计输出契约（对照 [_shared/standards.md](../_shared/standards.md#十一-b对抗审计输出契约对齐-multi-agent-test-auditor)）

评审/审计结论**必须**返回下列 5 类之一：

- [ ] **未杀死的突变**：含突变位置（文件:行号）、突变类型（如 `≤→<`）、为什么现存用例无法发现
- [ ] **未覆盖的分支/状态转移**：含源码行号或状态图转移编号
- [ ] **具体反例**：输入参数 + 期望行为 + 实际行为 + 复现脚本
- [ ] **契约缺口**：消费者期望未被覆盖的契约字段
- [ ] **无条件通过**：必须附逐用例验证（每个用例杀死哪些突变、覆盖哪些分支、保护哪些状态转移）

禁止的审计输出（视为无效）：
- "覆盖很高了" / "看起来够" / "应该没问题" / "标准做法" / "常规覆盖足够"
- 任何没有具体突变/分支/反例/契约缺口的状态报告

> 简单评审场景（本 SKILL）可降级使用——只要求返回 5 类结论之一，不强制逐用例验证；复杂审计场景（核心业务流程/安全测试）必须严格按完整契约执行，建议直接转交 [multi-agent-test-auditor](../multi-agent-test-auditor/SKILL.md)。

### 完成闸门（复杂场景适用，对照 [_shared/standards.md](../_shared/standards.md#十一-c完成闸门复杂场景适用)）

简单评审场景：通过上述检查清单即可视为完成。

复杂审计场景必须额外通过下列闸门：

- [ ] 变异分数 ≥ 80%（Stryker / mutmut 全量跑）
- [ ] 行覆盖率 ≥ 85%
- [ ] 分支覆盖率 ≥ 75%
- [ ] 状态转移覆盖率 ≥ 90%
- [ ] 静态扫描 critical = 0（SonarQube / Semgrep / Snyk）
- [ ] 性能基线不退化（P95/P99/错误率）
- [ ] 独立审计签字 ≥ 3 人（不是用例作者）
- [ ] GOAL_STATE 终行输出 `GOAL_STATE: complete` 或 `GOAL_STATE: blocked_<reason>`

> 任一闸门未过 → 回到生成/审计流程，不允许宣布完成。`blocked_<reason>` 也是合法结果。

## 常见问题

### 完整性问题

#### 问题1：需求覆盖不全

**现象**：某些功能需求没有对应的测试用例

**原因**：
- 需求分析不完整
- 测试设计遗漏
- 需求变更未更新测试用例

**改进建议**：
- 完善需求分析
- 建立需求-测试用例映射表
- 定期更新测试用例

#### 问题2：边界覆盖不足

**现象**：缺少边界值测试用例

**原因**：
- 边界分析不充分
- 测试设计经验不足

**改进建议**：
- 加强边界分析
- 使用边界值分析技术
- 参考边界值测试用例模板

### 正确性问题

#### 问题1：测试步骤不清晰

**现象**：测试步骤描述模糊，难以执行

**原因**：
- 测试设计不细致
- 测试人员经验不足

**改进建议**：
- 细化测试步骤
- 使用操作指导语言
- 参考测试步骤模板

#### 问题2：预期结果不明确

**现象**：预期结果描述模糊，难以验证

**原因**：
- 需求理解不充分
- 验证标准不明确

**改进建议**：
- 明确验证标准
- 使用可验证的描述
- 参考预期结果模板

### 可执行性问题

#### 问题1：前置条件不明确

**现象**：测试用例缺少前置条件说明

**原因**：
- 测试设计不完整
- 依赖关系分析不充分

**改进建议**：
- 明确前置条件
- 分析依赖关系
- 建立测试环境准备指南

#### 问题2：依赖关系复杂

**现象**：测试用例之间存在复杂的依赖关系

**原因**：
- 测试设计不合理
- 测试用例耦合度高

**改进建议**：
- 简化依赖关系
- 降低测试用例耦合度
- 使用测试数据准备脚本

### 可维护性问题

#### 问题1：命名不规范

**现象**：测试用例命名不符合规范

**原因**：
- 缺少命名规范
- 规范执行不严格

**改进建议**：
- 制定命名规范
- 严格执行规范
- 定期检查命名

#### 问题2：复用性差

**现象**：测试用例难以复用

**原因**：
- 测试用例设计不合理
- 缺少参数化设计

**改进建议**：
- 使用参数化设计
- 提取公共测试步骤
- 建立测试用例库

## 改进建议

### 完整性改进

#### 建议方法
1. **建立需求-测试用例映射表**
   - 确保每个需求都有对应的测试用例
   - 定期更新映射表

2. **使用测试设计技术**
   - 等价类划分
   - 边界值分析
   - 场景法

3. **定期评审测试用例**
   - 需求变更时更新测试用例
   - 定期检查测试用例覆盖

### 正确性改进

#### 建议方法
1. **细化测试步骤**
   - 使用操作指导语言
   - 明确每个操作的具体内容

2. **明确预期结果**
   - 使用可验证的描述
   - 明确验证标准

3. **验证测试数据**
   - 确保测试数据符合业务规则
   - 覆盖边界条件和异常数据

### 可执行性改进

#### 建议方法
1. **明确前置条件**
   - 列出所有前置条件
   - 确保前置条件可满足

2. **简化依赖关系**
   - 降低测试用例耦合度
   - 使用测试数据准备脚本

3. **提供测试环境准备指南**
   - 明确测试环境要求
   - 提供环境配置步骤

### 可维护性改进

#### 建议方法
1. **制定命名规范**
   - 制定测试用例命名规范
   - 严格执行规范

2. **提高复用性**
   - 使用参数化设计
   - 提取公共测试步骤
   - 建立测试用例库

3. **优化测试用例结构**
   - 合理分组测试用例
   - 保持测试用例层次分明

- 发现命名问题时，推荐查询命名规范
- 发现可维护性问题时，推荐查询可维护性最佳实践
